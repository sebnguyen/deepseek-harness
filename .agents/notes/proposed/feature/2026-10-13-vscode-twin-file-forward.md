# Agent Note: VS Code twin file-forward — delivered cards and snapshot chips open inside the frame

Status: proposed

## Problem

Every file-open the product issues — deliverable-card clicks (`ui-deliverables`), snapshot chips (`ui-primitives` `@path#turn#callId`, `ui-chat` `TurnChipRow`), and the reference browser — travels one seam: `openFile(path, options)` in `packages/client/ui-chat/src/client/contract/slots.ts` → `ctx.sidebarRight.openResource(dsh-resource://file/session/…)`. The `vscode` tab type claims that glob at the `extension` priority band (`packages/client/ui-vscode/src/client/definition.ts:24-32`), one above the CodeMirror editor's `builtin`, so with a twin running the tab that mounts is the VS Code iframe.

That claim is currently a dead end. `VscodeBody` builds `url/?tkn=<token>&folder=<workspaceRoot>` from `ideBridge.status` (`packages/client/ui-vscode/src/client/VscodeBody.tsx:95-104`) and ignores `tab.contentId` beyond reading its session id: the twin boots to its last workbench state, not to the file the user clicked, and `line` and `display/stop` navigation params never move. Worse, `keep-alive.tsx` parks one frame per workspace root, so a second file click on the same workspace adopts the same live frame — and nothing re-navigates it. Both package READMEs already reserve this layer under one name (`vscodeBridge.hello`, "file-forward signals", close confirmation: `packages/client/ui-vscode/README.md`, `packages/api/ide/README.md`), and the [twin architecture note](../architecture/2026-10-09-embedded-vscode-reh-editor-frame.md) scopes a full `dsh-vscode-bridge` extension whose `ide.open` downlink solves this among other jobs. Until either lands, the product's most-clicked file affordances point at the frame and do nothing observable.

## Proposal

Ship the file-forward half as the first consumer of the [twin cordis-seat bridge](../architecture/2026-10-13-vscode-twin-extension-cordis-seat.md): the host's `ideBridge` gains `open(sessionId, { path, line? })` and a `downlink` stream, and the twin's staged bridge extension mounts the minimal client seat, receives `{type:'ideBridge/open', path, line?}` frames privately, and calls `vscode.window.showTextDocument`. No fork workbench change, no iframe `postMessage` listener; the vscode-fork workbench contribution from the original draft survives only as the DOM-level layer for later features (close-confirm, back/forward). Envelope, auth, and extension-reusability details live in the linked note; this note keeps only the forwarder-facing decisions.

1. **Client forwarder (`ui-vscode`).** As landed: `src/client/forward.ts` derives `{sessionId, path}` purely (`forwardRequestOf`) from `parseFileAddress(tab.contentId)`, and `useVscodeAddressForward` fires one `remote.ideBridge.open(sessionId, { path })` per changed address once the twin reports ready; the wire's optional `line` rides in the host codec already (`IdeBridgeOpenRequest.line`) but the forwarder does not send it yet — line-notes' reveal lands when `tab.navigation.params.line` joins the request in a follow-up.
2. **Twin-side receiver.** None of this note's code: the seat's downlink loop maps `ideBridge/open` to `showTextDocument(Uri.file(path), { selection })`; absolute resolution is safe because the frame boots with `folder=<workspaceRoot>` on the same loopback machine.
3. **Navigation semantics at the seat.** The sidebar focuses an identical `(kind, address)` tab instead of re-seating (`ui-sidebar-right/src/client/service.ts:326-337`), so repeated opens of one file must still forward; the landed forwarder dedupes on the `${sessionId}:${path}` request identity (a `useRef` last-forward key inside `useVscodeAddressForward`) so parked-frame adoption during a session switch does not replay a stale open, while a click re-opening the SAME address stays a no-op (the identity compare has no line term yet — see item 1).
4. **Scope: plain file opening only.** The forwarder drops every other navigation param. Snapshot chips (`display: 'changes'`, `stop: callId`) forward as a **simple file open** — the chip lands on the current file in the frame, the frozen-stop semantics deferred to a later note pairing the changes display with the frame's checkpoint/timeline surfaces — and `@path#L<line>` line-notes forward with their reveal line. Any param the frame cannot honor is dropped silently for now rather than routed around it.

## Alternatives considered

- **postMessage into the iframe + fork workbench contribution.** The first draft of this note's carrier: a `dsh.vscodeBridge.open` window message answered by a `src/vs/workbench/contrib/dshBridge/` listener calling `IEditorService.openEditor`. Payable — but it costs a vscode rebuild + ring-3 rebase entry to deliver a file-open, when the same payload rides the seat's `downlink` with zero vscode-tree diff. Deferred to DOM-level features only.
- **Loopback HTTP owned by the staged extension.** Shrink the seat to one `http.createServer` in the staged boot extension taking `POST /open` and calling `showTextDocument`. Smallest possible (~300 LOC), and orphaned the moment uplink events arrive: every later vscode-plane feature still builds the seat. The bridge note absorbs it as the descoped lower bound, not the destination.
- **Land the full `dsh-vscode-bridge` extension first.** The [twin architecture note's](../architecture/2026-10-09-embedded-vscode-reh-editor-frame.md) settled endpoint; the [cordis-seat note](../architecture/2026-10-13-vscode-twin-extension-cordis-seat.md) is its descoped first slice, so "wait for the full bridge" now means waiting for a strictly larger version of the chosen carrier.
- **Reload the iframe with a file-bearing URL.** REH-web's boot query carries `folder`/`workspace` only; no file parameter exists in the served `webClientServer`, verified in the pinned `../vscode` tree. Reload-per-click would also destroy the keep-alive posture (`ui-vscode/README.md` makes the no-reload frame the feature). Ruled out.
- **`vscode://` / open-in-editor deeplinks and OS-level open.** No `vscode://` handler exists anywhere in this tree (the only match is a JSON-schema URI in `api/ide/src/twin-theme.ts`), and the native `SessionOpenWorkspacePathRequest` seam opens outside the product entirely — wrong destination for an embedded-editor claim.
- **Route snapshot chips to the editor tab claim instead of forwarding.** The first draft of this note kept `display: 'changes'` / `stop` opens on the ui-editor's frozen Changes surface until the frame can render checkpoint state. The product call settled the other way: the chip behaves as a simple file open in the frame, and the frozen-stop journey pauses for twin-ready deployments rather than splitting the chip's destination by twin state. Frame-side equivalents land with the checkpoint/timeline work later.
- **Extension-level `postMessage` listener.** The staged boot extension runs in the server-side (Node) extension host with no `window` access, so it cannot observe page-level `postMessage` at all — which is why the seat rides `/api` + `/api/remote.mux` instead of iframe messages, and why a fork workbench listener remained the only postMessage-capable party in the original draft.

## Acceptance criteria

- With a ready twin, clicking a delivered card's file, a `@path#L<line>` line-note, or a snapshot chip opens that file in the twin frame (the line-note at its line); the snapshot chip carries no frozen-stop state, opening the file as a plain edit.
- Two files opened in sequence on one workspace navigate the same adopted frame without a reload; a session switch and switch-back does not replay the last open (the frame stays wherever the user left it).
- `iframe` and twin absent: every route degrades to today's behavior (`ui-editor` / text preview claim) with no new failure surface; the seat's `downlink` consumer drops unknown frames and the host drops stale twin streams at disconnect.
- The fork diff is exactly one new contribution directory plus its registration line, under the ring-three patch accounting the [twin architecture note](../architecture/2026-10-09-embedded-vscode-reh-editor-frame.md) maintains; `verify-agent-note-format` and `verify-client-ui-i18n` stay green for new client copy.

## Risks

The parked-frame keep-alive model is the sharp edge: a stale tab mounting a live frame must not re-open its file over whatever the user navigated to since, which is why the forwarder keys on navigation identity rather than mount. The carrier itself — seat, bearer branch, downlink stream — takes its own risks in the linked architecture note; this note's residual exposure is only the forwarder's debounce semantics and the now-recorded drift risk that the two notes' open-frame shapes diverge, pinned by keeping exactly one envelope: `ideBridge/open { path, line? }`.
