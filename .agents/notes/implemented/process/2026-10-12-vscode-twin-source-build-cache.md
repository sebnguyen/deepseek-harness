# Agent Note: VS Code twin source-built per machine into the DSH-home cache

Status: implemented

## Problem

`dsh web` mounts its embedded VS Code editor only when a twin dist exists on disk, and the dist is a ~485MB build output the repository deliberately never vendors. Discovery found only three slots, all relative to the repository root (`../vscode-reh-web-linux-x64`, `../.vscode-twin/dist`, `.vscode-twin/dist`), and the recipe that produces one — clone the dsh vscode fork, `npm ci`, `gulp vscode-reh-web-linux-x64` — lived only in [DSH-BUILD.md](https://github.com/sebnguyen/openvscode-server/blob/dsh-build/DSH-BUILD.md) inside the sibling checkout. A fresh clone of just this repository therefore silently kept the fallback editor: nothing fetched the vscode fork, nothing built the lane, and no shared location existed for a built twin to survive across clones and worktrees. The higher-level question — should clones build the twin locally or download a prebuilt one — had no recorded owner.

## Decision

The twin is built from source on the machine that runs `pnpm dsh web`, never packaged or distributed, and cached machine-wide under the harness home:

- `scripts/bootstrap-vscode-twin.sh` (root script `pnpm run vscode:twin`) owns the whole loop: clone or refresh `$DSH_HOME/cache/vscode-source/<repo>` from the pinned fork (`DSH_VSCODE_TWIN_REPO`, default `git@github.com:sebnguyen/openvscode-server.git`) at a pinned ref (`DSH_VSCODE_TWIN_REF`, default `dsh-build`), `npm ci` only when `vscode-twin/install-stamp` does not match the lockfiles, npmrc files, and Node version (otherwise `out/` stays and `npm run compile` is incremental), then the host's `vscode-reh-web-${platform}-${arch}` gulp lane — Linux and macOS (Intel and Apple silicon) today, Windows hosts run it through WSL2 — and finally an atomic swap of the lane output into `$DSH_HOME/cache/vscode-twin/dist` (default `~/.dsh/cache/vscode-twin/dist`). Every artifact stays below the cache root; logs land in `vscode-twin/logs/`; the built commit is recorded at `dist/.dsh-source.json`. `--fetch-only` stops after the clone/refresh and the allowScripts strip, so a fetch does not need the compile toolchain.
- `findTwinDist` (`packages/api/ide/src/twin-dist.ts`) gains a fourth, last-precedence candidate: that same cache slot, resolved through `dshCachePath('vscode-twin', 'dist')`. An explicit `DSH_VSCODE_TWIN_DIST` row still wins over everything, and every repo-relative staged slot still wins over the cache, so a developer's local staging is never shadowed by a stale machine cache. Root `postbuild` runs `pnpm run vscode:twin` after `pnpm run build`, and skips that hook when `CI` is set so hosted jobs that invoke `pnpm run build` do not compile the fork. A fresh clone that has run `pnpm run build` once mounts the editor tab with zero configuration on any checkout of the machine.
- The script fails loudly on missing machine prerequisites (node 24.18+, git, disk, plus the OS toolchain — gcc/g++ and libkrb5 headers on Linux, Xcode CLT clang on macOS) rather than producing a half-usable dist, retries each network stage (clone, fetch, npm ci, compile, gulp) against transient timeouts before failing, and rebuilds replace the cache by `mv`-swap only after a lane finishes, so discovery never sees a partial tree. `DSH_VSCODE_TWIN_LANE` overrides the derived lane for cross-build checkouts.
- Desktop Electron natives are not compiled. On `dsh-build` the fork's root `.npmrc` has no Electron `target` (so preinstall does not download Electron headers) and root `allowScripts` is false, so root `npm ci` does not node-gyp that tree. The bootstrap still forces every root `allowScripts` entry false, and `remote` `@vscode/deviceid` false, by editing those booleans in place. `ELECTRON_SKIP_BINARY_DOWNLOAD=1` skips the Electron binary download. `remote/.npmrc` stays `runtime=node`, and `gulp vscode-reh-web-*` packages `remote/node_modules`, which still builds `node-pty`, `kerberos`, `spdlog`, `sqlite3`, ripgrep, the watcher, watchdog, `@vscode/fs-copyfile`, and `@vscode/policy-watcher`. Those last two stay because the server policy service and agent-host git load them. `playwright` stays importable for `src/vs/platform/browserView`; only its Chromium download script is off. Lockfile dependencies stay so `npm run compile` can still type `electron` and `native-keymap`.

## Alternatives considered

- **Publish a prebuilt tarball and fetch it (Playwright/esbuild posture).** The owner rejected release plumbing outright: a versioned artifact feed would force a release + manifest bump for every vscode-side commit, and the twin is maintainer-built editor chrome, not a redistributable product. A fetch layer turns a missing build into a silent one, widening the gap this note exists to close.
- **Platform packages as npm optional dependencies** (`@…/vscode-twin-linux-x64`, the `@esbuild/linux-x64` pattern). npm is the wrong transport for a ~485MB dist, `pnpm install` would drag it for every consumer (doc server, CI lint jobs), and publishing still required the release machinery the owner declined. A GitHub Release asset (on this repo or the fork) avoids npm's size limits but installs the same per-version release plumbing; it stays first in line if distribution ever becomes a real requirement.
- **A Docker image for the whole editor seat.** Changes the host-spawn contract — `packages/api/ide` execs `bin/code-server-oss` as a child process — and adds a Docker dependency to a web dev loop that should need nothing but node. The image would still need the same source build inside it, so it simplifies nothing about producing the artifact.
- **Vendor the dist in the repository (or git-lfs).** 485MB of build output among editable source, versioned forever, with every rebuild rewriting history. Vendoring is why the dist was always staged out-of-tree in the first place.

## Consequences

First run on a new machine pays one source build — roughly 20–40 minutes after the desktop strip, and ~10GB of transient space — and the machine must carry the compile toolchain (the script names each missing prerequisite). No release pipeline exists to feed or version, which is the point: the twin rule (client and server get stamped from one commit; see [the embedded frame note](../../proposed/architecture/2026-10-09-embedded-vscode-reh-editor-frame.md)) holds by construction because every consumer compiles the pinned fork commit itself. `pnpm run dsh web` on any checkout behaves identically: explicit config wins, then local staging, then the shared home cache. Old or foreign caches are never shadowed — each clone's `..` slots beat the cache. Keeping [the per-workspace keepalive](../feature/2026-10-12-workspace-keyed-twin-keepalive.md) unchanged, a second `pnpm dsh web` on the same workspace still reuses the same twin.

## Testing

`packages/api/ide/tests/twin-dist.host.spec.ts` pins the cache slot's last place in `twinDistCandidates`, its discoverability from an empty `$DSH_HOME`-stubbed root, and its precedence losing to any repo-local slot. The bootstrap path itself is validated on the maintainer machine by running `pnpm run vscode:twin` from this checkout: a fresh clone through the swap into `~/.dsh/cache/vscode-twin/dist`, after which `findTwinDist` resolves exactly that slot. Validation covered linux-x64; the lane-name parameterization is host-derived and follows the same `vscode-reh-web-<platform>-<arch>` task matrix, but the darwin lanes are unexercised hardware-wise as of this note.
