# Agent Note: The web tab and desktop window carry the teal pixel mark

Status: implemented

## Problem

Two brand surfaces still carried the pre-pixel artwork after the DigitalOcean rebrand. `apps/web/public/favicon.svg` was a white vector whale, which disappears against light browser chrome, and `apps/desktop/resources/icon-windows.svg` was a white vector glyph on a `#0069FF` tile. The product already ships the DigitalOcean mark as a 16x16 pixel silhouette, colored teal `#7BB4BC` in the Atlas shell; the tab and window icons should use that face instead of maintaining a second vector rendering.

## Decision

`design/pixel-do-loader-gen.mjs` now writes two outputs from the same derived 16x16 grid as the sweep and twinkle faces:

- `apps/web/public/favicon.svg` — a solid teal mark on transparency, 64x64 intrinsic with a 16x16 viewBox. It serves the browser tab and the existing PWA manifest icon.
- `apps/desktop/resources/icon-windows.svg` — the same mark at 800x800 inside a transparent 1024x1024 canvas, wrapped in `tray-glyph` so `render-tray-icon.ts` can enlarge it 1.2x for the 16-64 px tray bitmaps.

The cell gap is geometry: each cell is a `0.8x0.8` rect at a `0.1` inset, not `clip-path: inset(10%)`. sharp's librsvg rasterizer ignores the CSS clip-path, which would render the desktop cells solid; the explicit rects keep the same 20% gap in every host, including the browser.

`pnpm run render:tray-icon` in `apps/desktop` regenerates the committed `icon-windows.png` and `tray-windows.ico`. The teal mark is used unchanged in light and dark schemes; `#7BB4BC` is legible on both, so the favicon has no `prefers-color-scheme` fork.

## Alternatives considered

**Keep the white vector mark and the blue tile.** The tile kept the white glyph readable on light taskbars, but it is a second brand color and a second geometry. The product's shipped face is the pixel grid, and the replacement uses a transparent ground.

**Use `clip-path: inset(10%)` for the gaps.** It is the existing browser geometry and would keep the markup identical to `PixelMark`, but sharp/librsvg ignores `inset()` on SVG rects: the tray and application rasters would lose their pixel gaps. The explicit 0.8-unit rects render the same gaps everywhere.

**Animate the favicon with the twinkle face.** The idle letterpress is a 260 px animation at 22% opacity. In a 16 px tab it would be both faint and flickering. The solid silhouette is the mark at favicon size.

## Consequences

The tab and Windows window/taskbar icons are now the solid teal pixel mark; the favicon is no longer a white vector path and the window icon no longer carries a blue tile. Both assets are derived from the pixel pipeline, so changing the mark means rerunning `node design/pixel-do-loader-gen.mjs` and then `pnpm run render:tray-icon`.

The committed raster artifacts still have to be regenerated by hand after a source change; `tests/tray-icon.spec.ts` checks the ICO roster and PNG stream shape, not whether the bytes match the source. `apps/web/tests/pwa-manifest.e2e.ts` still asserts the pre-rebrand `DeepSeek Harness` manifest and a black/white favicon; that test was already stale for the DigitalOcean rebrand and this change does not update it.

## Testing

- `node design/pixel-logo-pipeline-check.mjs` — the 16x16 grid still matches the coverage derivation from `website/public/favicon.svg`.
- `pnpm run render:tray-icon` in `apps/desktop` — wrote the 1024 px PNG and the seven-entry ICO; a second run is byte-stable.
- `pnpm exec vitest run apps/desktop/tests/tray-icon.spec.ts` — three tests pass.
- Chromium (Playwright, `/usr/bin/chromium-browser`) rendered the favicon at 16/32/64/256 px and the window source at 16/32/64/256 px: the favicon fills its viewBox, the window mark keeps its centered margin, every sample has a transparent ground, and fully opaque teal `rgb(123, 180, 188)` appears from 64 px; 16 px is partial alpha as expected for a 16x16 grid.
- Node/sharp read the committed `icon-windows.png`: 1024x1024 RGBA, 185,600 lit pixels (116 cells at 50x50 px), all exactly `#7BB4BC`, 862,976 transparent pixels; every ICO entry is 16-64 px with a transparent ground.
