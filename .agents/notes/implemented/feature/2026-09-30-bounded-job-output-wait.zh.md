# Agent Note: 有界的 job_output 等待

Status: implemented

[English](2026-09-30-bounded-job-output-wait.md) | 中文

## 问题

仅快照的 `job_output` 读取让真正被阻塞的 agent 无从等待：一个在任务结算前无法继续的 agent 要么结束本轮、依赖完成通知，要么循环读取快照。通知通路会让空闲所有者被唤醒一轮来得到答案，但繁忙所有者只会在下一步的边界领取通知，而一个在中途需要结果的步骤则每次轮询都要花掉一步。这次移除同时丢掉了让历史上的阻塞读取保持安全的那个界限：等待曾由插件配置提供默认值并限定上限，因此阻塞调用不会无限期停滞一个步骤。

## 决策

`job_output` 恢复其阻塞读取，且现在每次调用都阻塞：每次读取都阻塞到任务进入终止状态或截止期，`timeout_ms` 是单次调用上唯一可由模型设定的界限。两个配置字段为所有等待设界：`waitTimeoutMs`（默认 10,000）在读取省略 `timeout_ms` 时生效，`maxWaitTimeoutMs`（默认 60,000）把模型给出的更大 `timeout_ms` 向下收敛到它；`waitTimeoutMs` 高于上限会在加载时失败。超时的读取返回带 `[status: running]` 的存活快照，任务保持存活；抵达终止状态的读取返回结算后的输出，并把任务标为已报告，与终止读取同样抑制冗余的完成通知。

该工具委托给 seam 方法 `JobRegistry.wait`，进程局部注册表以每任务的等待方簿记实现它：结算会在宣布完成之前释放存活的等待方，存活的等待方会在监听器运行之前把记录标为已报告，因此等待中的读取方与通知不会两次投递同一次完成。带 scope 的 deadline 原语区分等待超时与调用方取消，且读取遵循 `exec.signal`——被取消的步骤只在任务存活时让等待被拒绝，绝不取消任务本身。这反转了[仅快照的任务读取](../../archived/feature/2026-09-29-snapshot-only-job-reads.md)；[不消耗地观察任务输出](2026-09-29-observing-job-output-without-consuming-it.zh.md) 的非消费式观察者通路保持不变。

## 考虑的替代方案

- **保持仅快照读取，让被阻塞的 agent 轮询。** 否决：轮询在不变的状态上每次读取花掉一步，而繁忙所有者最终领取的通知比有界读取返回同一结果晚一步。1 分钟上限让阻塞读取的代价保持有限。
- **与快照读取并列的可选或必填 `wait` 标志。** 否决：两种读取模式把同一个问题——结算并给我输出——拆成两种调用形态，而被客户端自动填充的可选形态会在不声明的情况下重建阻塞读取。始终阻塞把阻塞写进工具唯一的契约里。
- **恢复历史上 10 分钟的上限。** 否决：模型自行选择的超时必须保持在步骤量级附近，因此出厂的 `maxWaitTimeoutMs` 默认值为 1 分钟；该字段保持可配置，供确需移动界限的部署使用。

## 后果

完成通知仍是超时的读取的完成信号：超时的读取让通知继续欠着，只有 kill、终止读取（包括等待到终止状态的读取）、或 teardown 取消会把记录标为已报告。超时的读取是一次成功的观察而非错误——它返回 `[status: running]`，因此工具自己拥有截止期，而不是交给通用工具超时策略，后者会把这次观察替换成超时错误。被阻塞的步骤至多付出封顶的超时，因此系统提示引导语把收取表述为：用 `job_output` 收取仍相关的任务，其每次读取都阻塞到结算或有界超时，并返回存活状态以待通知跟随。

## 验证

`packages/jobs/tool-jobs/tests/tool-jobs.spec.ts` 固定工具契约：schema 仅暴露 `job_id`（必填）与可选的 `timeout_ms`；对存活任务的读取在配置的界限到期并返回存活状态；读取阻塞到结算并报告终止状态；模型给出的超时高于上限时向下收敛；递送了终止状态的读取抑制通知，而超时的读取仍让通知欠着。`packages/jobs/jobs-local/tests/jobs.spec.ts` 固定 seam：结算以已报告状态解析等待方；超时在不报告的情况下解析存活状态；超时与被中止的解析器在任务保持存活时注销；同一 tick 内与结算竞争的 abort 会在通知被决定之前移除等待方；`wait` 以拥有者会话为界。`packages/jobs/jobs/tests/service.spec.ts` 在 stub 注册表上覆盖该 seam 方法。
