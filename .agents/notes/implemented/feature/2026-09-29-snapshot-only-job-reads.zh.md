# Agent Note: 仅快照的任务读取

Status: implemented

[English](2026-09-29-snapshot-only-job-reads.md) | 中文

## 问题

`job_output` 接受 `wait: true` 与可选的 `timeout_ms`，会把当前步骤阻塞到任务结算或截止时间到期（`waitTimeoutMs`，上限为 `maxWaitTimeoutMs`）。该参数存在的原因是：阻塞式读取曾经是模型得知后台任务已完成的唯一途径。完成通知取代了它：[后台任务完成唤醒空闲所有者](2026-08-11-background-job-completion-wakes-an-idle-owner.zh.md) 让结算以会话内消息送达拥有该任务的 agent，而周围的指引被压缩为要求模型「只在确实被阻塞时」使用阻塞式读取——这是机制强加给调用方的判断，而不是机制自己回答的问题。

阻塞式读取也与任务的目的相矛盾。agent 启动后台工作是为了能继续推进；而会等待的读取恰好在 agent 刻意回避等待的时刻把等待还给它，并消耗掉完成通知本就要省下的那一步。

## 决策

`job_output` 只接受一个参数 `job_id`，并且始终返回非阻塞快照：流式任务返回自上次读取以来的输出，最终输出任务在结算后返回其结果，每个响应都以 `[status: ...]` 结尾。稍后才结束的运行通过既有的完成通知送达 agent——agent 繁忙时注入其下一步收件箱，空闲时以有界的 follow-up 轮次唤醒。

`JobRegistry.wait` 方法一并移除，本地注册表的等待方计数、等待方解析器与结算时释放也一同删除。把记录标为已报告的标记仍是终止读取与取消：已经返回终止状态的读取让完成通知变得多余，而模型主动终止的任务不需要完成消息。`waitTimeoutMs` 与 `maxWaitTimeoutMs` 这两个 tool-jobs 配置字段只用于约束被移除的等待，因此随之消失。

## 备选方案

- **保留 `wait: true` 作为确实被阻塞的调用方的显式选择。** 拒绝，因为通知已经回答了它被保留下来要回答的问题：确实无法推进的模型，其下一步已有排队的通知；能够推进的模型不该被提供一个让它停下的控制项。同时保留两者会留下两个完成信号，而它们之间的交互——一次等待会报告任务并抑制其通知——必须在每次读取时被重新推演。
- **只移除工具参数，保留 `JobRegistry.wait` 作为接缝方法。** 拒绝，因为这会留下一个没有生产消费方的公共方法，而它的等待方簿记只用于在等待交付终止状态时把记录标为已报告。终止读取已经承担该规则，因此该方法会是没有用处的负担，却带着看似有效的约定。
- **把等待缩短为固定的短超时，而不是移除。** 拒绝，因为这是更差的约定：有界的阻塞式读取仍然会停顿该步骤，而很短的界限把「确实被阻塞」变成与任意数字的竞速。

## 后果

仍然传入 `wait` 或 `timeout_ms` 的调用方会得到普通快照：工具两者都不再声明，而未声明的参数会被忽略而不是被拒绝，因此被移除的参数降级为一次非阻塞读取，而不是报错。需要已结算输出的测试——一次性后台 subagent 场景与已交付组合的后台场景——现在等待记录，而不是要求一次读取去等待，这正是真实调用方从完成通知得到的同一种顺序。

必须在不动用模型游标的前提下跟随输出的观察者改为按行读取：见[在不消耗输出的前提下观察任务输出](2026-09-29-observing-job-output-without-consuming-it.zh.md)。

移除阻塞式读取也移除了 `JobRegistry.wait` 最后一个生产消费方，因此接缝方法与其簿记在同一次改动中删除，而不是为兼容性保留。

## 验证

`packages/jobs/tool-jobs/tests/tool-jobs.spec.ts` 钉住快照约定：对运行中任务的读取返回 `[status: running]` 且不阻塞，已结算的读取返回最终输出，被移除的参数产生同样的快照，运行中的读取不再抑制完成通知。`packages/jobs/jobs-local/tests/jobs.spec.ts` 与 `packages/jobs/jobs/tests/service.spec.ts` 覆盖不含该方法的接缝。
