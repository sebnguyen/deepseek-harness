# Agent Note: 在不消耗输出的前提下观察任务输出

Status: implemented

[English](2026-09-29-observing-job-output-without-consuming-it.md) | 中文

## 问题

任务输出原本只有一条通路：`JobRegistry.read` 推进唯一的消费式游标，或 `readOutput` 产出增量。该游标属于模型——`job_output` 正是把任务输出变成工具结果的那一步——因此任何其他想跟随运行中任务输出的东西，都会拿走模型仍然应得的字节。于是浏览器视图、状态行或实时 tail 只能通过窃取模型的流来构建，或者等结算后再读取保留的副本。

被这件事挡住的第二个消费方，正是即将出现的那个：Web 客户端按任务展开的详情视图，以及为它提供数据的会话控制帧。

## 决策

`JobHooks` 新增可选的 `readLines(from)`：按绝对行号提供保留的输出行，且不触碰消费式游标。`JobRegistry.readLines(id, caller, from)` 以与其他操作相同的所有者隔离把它投射出来，并且刻意不把任务标为已报告——观察输出的人不是得知结果的模型，因此完成通知仍然欠着。

行号是相对于该工作自身行流的绝对索引；当调用方要的行已被丢弃时，生产方会报告 `truncated`。因此从前端裁剪的缓冲区绝不会悄悄把调用方的游标挪到不同的行上，而相对的窗口会。能够回答这件事的生产方是持有可寻址缓冲区的那个——持久化 shell 的任务，它的保留文本本就每次轮询都从 terminal 按行寻址的 scrollback 重新推导出来。

缺失本身有意义，而不是降级：输出只作为流存在的生产方（管道支撑的命令、subagent）不提供 `readLines`，此时 `JobRegistry.readLines` 返回 undefined。这个面由生产方决定是否提供，与 `readOutput` 现有的规则完全一致。

## 备选方案

- **让观察者调用 `read` 并转发它所消费的内容。** 拒绝：这会以观察者的名义花掉模型的游标，因此一个开着后台任务输出的浏览器标签页会悄悄掏空 agent 随后读取的工具结果。
- **让 `read` 给每个调用方返回一份副本。** 拒绝：`read` 的唯一游标正是让流增量有定义的东西。一个增量的两个消费方不可能都收到「自上次读取以来」的内容——按构造，第二次读取是空的。
- **在观察者里直接读 terminal 服务。** 拒绝，因为浏览器与帧发布方都没有 terminal 会话：它们持有的是任务 id，而让任务可读的所有者隔离存在于注册表中。
- **只推送已结算的输出。** 拒绝，因为它回答错了问题：打开一个运行中任务的输出的理由，正是它还在运行。

## 后果

模型自己的通路仍是[仅快照的任务读取](2026-09-29-snapshot-only-job-reads.zh.md)，它移除了阻塞式等待；这次新增的读取是与之并列的观察者通路。

注册表的 `readLines` 是除 `get`/`list` 快照之外的第二个非消费式接口，也是唯一携带大块文本的那个；轮询它的调用方必须自己持有游标，这正是返回值携带 `next` 而不是页序号的原因。

只有当工具的发送至少结算过一次之后，命令的输出才变得可读——保留文本是在工具的轮询节奏上重新推导的，而一次发送会在后端的静默窗口或命令结束时结算。短于该窗口的命令会一次性发布其输出，这是既有流式通路的性质，而不是这次读取的性质。

## 验证

`packages/jobs/jobs-local/tests/jobs.spec.ts` 钉住注册表约定：按绝对索引取页、游标不变时结果可重复、更靠后的游标只看到其后的内容、模型自己的消费式读取随后仍返回完整流、被丢弃的行会被告知而不是被静默跳过、外部观察者被拒绝，以及没有可寻址缓冲区的生产方返回 undefined。`packages/shell/tool-bash-persistent/tests/background.spec.ts` 通过真实 Loader 组合做端到端验证：观察者在命令仍在运行时读到第一行，此时取下的游标只读到其后的那一行，而模型的 `job_output` 仍然收到两行。
