# Agent Note: 把运行中的命令提升为任务

Status: implemented

[English](2026-09-29-promoting-a-running-command-to-a-job.md) | 中文

## 问题

持久化 shell 是 agent 唯一的 shell，而一条命令就占满了它。长期运行的前台命令因此付出双份代价：之后每一次 `bash` 调用都排在工具按所有者串行的队列里，而单命令截止时间（`timeoutMs`）最终会关闭 shell 并销毁工作，因为截止时间唯一可用的动作就是重置。agent 无法把已经开始运行的命令交给 `ctx.jobs`——`run_in_background` 在命令存在之前就做出了决定——也无法在不丢失工作的情况下终止并重启它。

## 决策

超过 `backgroundAfterMs`（默认 `10000`）的前台命令会被移交为后台任务，而不是继续占用 shell。没有任何东西被搬动或重启：命令已经在会话中运行，因此任务接管它的观察、完成与关闭，工作继续推进，agent 的下一次 `bash` 调用会启动一个新的 shell。

当一条命令运行期间有第二条 `bash` 调用到达时，门槛会降到 `contentionAfterMs`（默认 `1000`）。按所有者的队列会发布这个等待中的调用，持有者随即以更低的门槛重新赛跑，而不是让调用方等完一条它已不再需要观察的命令。竞争只是压低门槛而不是取消它，因此在门槛内结束的命令仍以自己的输出服务自己的调用方，确认文本也会说明「shell 被需要」而不是「命令太慢」。`contentionAfterMs: 0` 只保留阈值，`backgroundAfterMs: 0` 则两者都关闭。

工具让进行中的发送与阈值赛跑，而不是向它发信号。赛跑失败只放弃工具自身的观察——没有任何信号抵达命令——这正是提升得以成立的原因：它所取代的截止时间路径用的是 `reset`，而 `reset` 会关闭会话。

注册先于退役。`ctx.jobs.start` 先运行，只有注册成功才调用 `retire`，因此被拒绝的注册（所有者任务上限已满，或没有已挂载的控制器）会让命令留在 agent 自己的 shell 中继续运行，调用正常结束。先退役会让 agent 既没有 shell 也没有任务。

`retire` 是工具按所有者作用域的 shell 注册表上的新操作，与 `get`、`reset` 并列：它删除该所有者的条目而不关闭会话，把关闭责任交给采用方。被拒绝的提升还必须*恢复它所放弃的那次发送*，而不是再发起一次：一个 terminal 会话只允许一次活动发送，因此新的 `startSend` 会以 `SEND_ACTIVE` 被拒绝，而失败路径会重置 shell——销毁这次拒绝本应保住的命令。

确认文本会指出任务 id、说明 shell 已被替换，并指向 `job_output`，因此模型读到的是有意的移交，而不是一条失败的命令。它包含的 shell 替换说明与 `exit` 或重置产生的说明相同。

## 备选方案

- **按竞争而不是按阈值提升。** 已被「两者都交付」取代：竞争现在是第二个触发条件，按所有者的队列会把它发布出来。保留此条是为了记录在该信号尚不存在时为何需要它。
- **保留截止时间，到阈值就杀掉。** 拒绝：这会销毁构建、测试运行与安装，而提升的存在正是为了避免这一结果。
- **把做到一半的命令搬进新的后台会话。** 作为不可能而拒绝：运行中的进程无法被重新归属到另一个 PTY，重启它则会重做副作用。
- **让命令在自己的会话中启动，不动 agent 的 shell。** 拒绝，因为该命令会失去持久化 shell 之所以有价值的那些状态——`export` 的环境、已激活的 virtualenv、`cd` 到的目录——而 agent 会在不知情的情况下得到与它自己构建的不同的环境。

## 后果

只有当 `backgroundAfterMs` 小于 `timeoutMs` 时提升才会触发；等于或大于时，截止时间仍会先结束命令，README 已说明这一点。被提升命令的 shell 保留着 agent 不再共享的状态，因此移交会说明 shell 已被替换，而不是让模型去推断。在阈值内结束的命令不受影响，短命令的输出仍留在工具结果中。

阈值是部署配置，默认 10 秒。录制会话中运行超过该时长的命令，现在会观察到确认文本而不是录制时的命令输出，因此它们的期望属于待处理的快照重录。

## 验证

`packages/shell/tool-bash-persistent/tests/promotion.spec.ts` 在真实 Loader 组合上证明了两半：超过阈值的命令返回确认文本，其输出在移交后通过 `job_output` 到达，下一次 `bash` 调用发现已导出的状态不复存在；而在所有者任务上限耗尽时，命令在前台以自身的退出状态结束，且不会注册第二个任务；排在运行中命令之后到达的第二次调用会以竞争确认文本将其移交，而在竞争门槛内结束的命令则在前台得到服务。`background.spec.ts` 继续覆盖共用同一组任务钩子的 `run_in_background` 路径。
