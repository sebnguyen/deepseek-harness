# Agent Note: DigitalOcean inference as a shipped provider with a model-tuning rail window

Status: implemented

## Problem

A DigitalOcean deployment is assembled today from a hand-maintained home-level patch: `apps/cli/config/examples/do-standard/cordis.yml` circulates as `~/.dsh/cordis.patch.yml` and declares the `digitalocean` route on `llm-pi-ai` (openai-completions against `https://inference.do-ai.run/v1`, the `max_completion_tokens` wire field, reasoning-content replay compat), an eleven-model catalog with per-model contextWindow, maxTokens, and reasoningEfforts, the deployment default selection (`agent-default-model`: digitalocean / deepseek-v4-flash-0731 / temperature 0.2), and the DO serverless rate table behind the cost chip. Every change — a new model, a corrected window, a different default — is a YAML edit outside the product, and a fresh checkout serves DeepSeek only.

The tuning facts a DO operator actually turns live on three disconnected surfaces: the deployment default in cordis config, the per-session sampling temperature in the composer's `conversation.input.temperature` slider (`session.selectModel`), and the per-model context window and max completion tokens in the Models settings page's catalog editor (`remote.settings.mutate` into the serving adapter's namespace). No surface next to the conversation groups "how the current model runs"; the Models page is deployment-wide catalog maintenance, and Settings is where the operator chose not to look for per-session tuning.

## Decision

Two changes ship together.

**Keep the base bundle dormant; ship the route where profiles already live.** The base bundle's `llm-pi-ai` row mounts the adapter with zero routes on purpose — which providers run is the user's settings document, and keyless snapshot and headless boots must never grow a route whose credential is absent. The `providers.digitalocean` profile therefore stays out of the base patch: `apps/cli/config/examples/do-standard/cordis.yml` remains the shipped composition for DO deployments, and for everyone else the tuning window itself writes the settings section (provider row, endpoint, key, Fetch specs adoption) on first pick. The shipped default stays DeepSeek-baked, and a DO deployment's default persists in the user layer on first pick rather than in shipped config. `llm-deepseek` stays mounted: a stored `DEEPSEEK_API_KEY` keeps the official route live beside a picked DO route, and the onboarding flow that recognizes the deepseek-official row is unchanged. The credential stays a typed key (`DO_INFERENCE_API_KEY` or the window's stored key via the credentials seam), never a bundle literal.

**A model-tuning rail window outside settings, folded into the selection plugin.** `ui-model-selection` registers a `settings.trigger-item` entry at `order: -10`, which the settings shell stacks above the Efficiency entry (order 0), opening a portaled window in the `TokenEfficiencyEntry`/`TokenEfficiencyWindow` pattern — no new package, because every face the window needs (the directory, the remotes, the settings mirror, the locale) is one the selection plugin and the Models page already own. The window reads the session's shared `ModelDirectory` and the route catalog, and writes through the existing durable paths:

- A provider select at the window head opens the joined configurable-provider directory — `llm/listProviders` joined with `llm/listConfigurableProviders`, the same join the Models page renders — so one window serves both adapter families: the llm-pi-ai family lists every configured route beside the installed catalog routes (digitalocean alongside openai, anthropic, …), the llm-deepseek family its single `deepseek-official` route; each menu row carries its persistence address (settings namespace and path, credential reference).
- The row under the picker exposes the three route facts the Models page's ProviderEditor carries: Format (the profile's `api` wire protocol, a select over the adapter's `supportedProtocols` union — `openai-completions`, `openai-responses`, `anthropic-messages` — with the llm-deepseek family pinning its own), Endpoint (the profile's `baseURL`, a write-in), and API Key (the credentials seam like Settings: a stored key renders masked behind its reference name, a missing one renders a typed input plus Save that stores the derived `<ROUTE>_API_KEY` reference). Same trio, same stores, same schema writes as Settings → Models.
- Below the picker, the selected route's catalog is one fixed-column table — Model, Temp, Effort, Context, Max, and a four-cell $/M block (in, out, cache read, cache write) — with every knob a write-in cell or an in-cell select: Temp, Context, and Max are primitives Input wraps (write-ins typed over the Models editor's validated vocabulary: temperature inside `[0, 1]`, capacities positive whole counts over `formatCapacity`/`parseCapacity`, max at most the row's own context, and context at most the route profile's `maxContextWindow`; the committed session temperature rides the shared selection projection for every adapter family — the agent's request merge spills it into `LlmCallConfig` and the `llm-pi-ai` adapter spreads `options.temperature` onto the wire, so the composer slider tunes the shipped pi LLM rather than a DeepSeek-only control), the four $/M cells (in, out, cache read, cache write) render the session-stats rates as static read-only text — pricing is rate data, not a knob, read through a `sessionStats.describePricing` remote the session-stats plugin registers alongside its cost chips — and Effort is the ModelSelect trigger chip opening its portaled radio menu over the model's levels. On the session's current-model row (brand-dotted), Temp and Effort are the live selection and commit through `session.selectModel` — the same coalesced commit the composer slider and the /model popup use. Every other row's Temp and Effort edit that model's stored tune: one new validated field on the route profile, merged into the `ModelSelection` when the model is chosen, with precedence session-explicit over stored tune over deployment default. Context and Max on any row write that model's capacity node of the serving route's profile (`providers/<route>/models` entry on a hand-declared route, `modelOverrides` on an untouched catalog route) through `remote.settings.mutate` — the same node, schema, and vocabulary the Models page's capacity editor writes, without switching the session's model. the static $/M text reads the same session-stats pricing map the cost chips and the Efficiency window render, so one rate table shows everywhere and corrections enter the pricing row, not the tuning table. Column-group heads (session tune / capacity / $ per Mtok) carry the scope signal; `settings/document-updated` and `llm/adapters-updated` keep the Models page, the window, and the chips converged.
- A header `Fetch specs` action is the Models page's `remote.llm.discoverModels`: endpoint interrogation fills id, contextWindow, and maxTokens for the models a gateway discloses. Adoption is additive-only, the same pre-unchecked rule the Models page applies: rows already in the profile keep every stored cell and the endpoint's numbers for a known id are discarded, so a prefetch never overwrites a corrected window, a stored tune, or the dotted row's session values; only ids the route does not list yet are appended, with the adapter's `DEFAULT_CONTEXT_WINDOW` and `DEFAULT_MAX_TOKENS` where the discovery omitted a capacity. Rates have no endpoint source — no supported gateway publishes pricing — so they arrive from the shipped per-route table (the DO docs table verified 2026-10-01); the window renders them read-only.

Copy rides en/zh dictionaries in a `model.tuning` namespace per the [locale-owned client UI copy](../../implemented/architecture/2026-08-23-locale-owned-client-ui-copy.md) decision, and the new `settings.trigger-item` occupant is re-emitted by `pnpm run gen-client-catalog`. The companion visual is `design/model-tuning-rail-mock.html`, which borrows the shipped chrome verbatim: the rail entry and window wear the TokenEfficiency entry/overlay/panel CSS, a provider select over the joined directory opens the window (menu pinned open in the mock, rows annotated with their settings address), the editable table rides the efficiency window's fixed-column pattern under a two-row grouped head, Temp/Context/Max cells are primitives Input wraps, the $/M cells are static text, Effort cells are ModelSelect trigger chips opening the portaled radio menu (one pinned open on the dotted row), the route row adds Format/Endpoint/API key exactly as the Models editor does, and every glyph is a shipped `ui-primitives` icon path.

## Shipped surface

The implemented pieces and where they live:

- **Stored tunes:** the `llm-pi-ai` route profile's `models[i]` entry accepts a validated `tunes` field (`temperature` inside `[0, 1]`, `reasoningEffort` one of the levels the model's `reasoningEfforts` map offers; a refusing config fails at catalog load). `resolveRouteModels` exposes the stored tunes as a `configuredTunes` map; the adapter's `modelInfo` then carries `defaultTemperature`, which `llm` materializes into `LlmCallConfig` as an adapter default flagged in `adapterDefaults.temperature`, so `agent.ts` already treats a tune-defaulted knob as non-explicit and the precedence explicit selection over tune over deployment default holds through logged-header restoration. `normalizeModelInfo` validates and carries `defaultTemperature` (`INVALID_MODEL_INFO` outside `[0, 1]`).
- **Pricing over the wire:** `session-stats` registers a `SessionStatsPricingController` typert remote whose `describePricing` returns the deployment's `CostPricing`; the window's $/M block and the cost chips read one table.
- **Capacity vocabulary:** `formatCapacity`, `parseCapacity`, and `deriveKeyRef` live in `ui-primitives` (React-free), shared by the Models page editors and the window's draft rules; the window's pure draft rules and settings path-op builders sit beside the window in `ui-model-selection/src/client/tuning/`.
- **The window:** `TuningEntry` (rail entry, `IconEnhanceOutline16`, order -10) and `TuningWindow` (portaled panel over the efficiency window's chrome) with a `TuningWindowStore` over the settings mirror's describe face; every commit rides `remote.settings.mutate` fenced by the namespace revision the draft opened at, `remote.credentials.set`, `remote.llm.discoverModels`, and `directory.select` for the dotted row; `settings/document-updated`, `credentials/reference-updated`, `llm/adapters-updated`, and `connection/reset` reload it once opened.
- **Gates:** `verify-client-ui-i18n`, `verify-client-catalog`, the module graph, and the package dependency gates stay green; unit specs cover the draft rules, the store's read/write lanes, and the window's render and additive fetch (`packages/client/ui-model-selection/tests/tuning-*.spec.*`, `packages/client/ui-primitives/tests/capacity.client.spec.ts`).

## Persistence and auto-fetch

The window reads four stores and writes three:

| Fact | Store | Written by |
|---|---|---|
| pi-ai route set and profiles (endpoint, protocol, catalog, capacities, tunes) | `llm-pi-ai` settings namespace, `providers.<route>` — the user layer of `$DSH_HOME/settings.yaml`, hot-reloaded | table cells, Models page, Models onboarding |
| Official DeepSeek route | `llm-deepseek` namespace | Models page |
| API keys | credentials seam (`$DSH_HOME/.credentials.yaml` over environment), referenced by `apiKeyEnv`, never stored in bundle config | Models page key field |
| Per-session selection (provider, model, effort, temperature) | Durable Session-log projection written by `session.selectModel` | dotted row cells, composer seat and slider, /model |
| Per-model pricing | the session-stats pricing row's `models` map, shipped in bundle config | read-only in the window; corrected at the pricing row |
| Route endpoint, wire protocol, key reference | the `llm-pi-ai` profile's `baseURL` / `api` / `apiKeyEnv` fields and the credentials seam | the window's route row and the Models page, schema-validated |

Specs auto-fill through `llm/discoverModels`: the llm-pi-ai `registerModelDiscovery` seam interrogates the route's `/models` endpoint and returns `LlmDiscoveredModel` ids with contextWindow and maxTokens, which the Fetch specs action adopts into the profile exactly as the Models page's adopt action does. Every write-in commits only after passing validation — temperature inside `[0, 1]`, capacity counts parseable from the K/M vocabulary, max at most the row's context, context at most `maxContextWindow`; a failing draft paints its cell and never touches the stored node. Pricing never auto-fills from an endpoint; it ships as the dated per-route table and stays read-only text in the window.

## Alternatives considered

**Why not a settings section or a tab inside Settings?** The operator asked for tuning out of Settings, and the structure agrees: `settings.section` is a deployment-wide page, while temperature and effort are per-session state a page would show without saying which session it names. The rail window is keyed by the viewed session exactly like the composer seats.

**Why not extend the Models page?** The Models page joins the configurable-provider directory and edits route catalogs; per-session tuning is not catalog maintenance, and the page sits a modal away from the conversation. Its capacity editor remains the deployment-grade authority the window reuses.

**Why not per-session capacity overrides in the LLM seam?** `GenerateOptions` and `ModelSelection` carry no contextWindow or maxTokens fields; both are adapter model metadata validated by `normalizeModelInfo`, so a session-scoped override forks every adapter's `resolveModel`. The settings-namespace write is the only capacity path with existing validation, UI vocabulary, and invalidation.

**Why not drop the composer temperature slider?** Rejected: the slider is the composer's quick access and the window is the grouped surface; both commit the same durable projection, so the two cannot disagree.

**Why keep `llm-deepseek` mounted?** Operator decision: the DO default must not dismantle the official DeepSeek route, and deployments with a stored key keep a working fallback plus the onboarding flow that already recognizes the deepseek-official row.

**Why not grouped per-session controls plus a separate capacity table (the rev 1–2 forms)?** The knobs split across two scopes, and tuning a model other than the current one required switching to it first. One row per model reads every fact about a model in a single pass; the dotted current row carries the only session-specific meaning the table needs.

## Consequences

- A fresh `dsh --profile web` boot with no home patch starts on the baked DeepSeek default and stays keyless; the do-standard example composes the DO route in one `--patch`, and the tuning window grows the same route into the user settings layer (provider row, endpoint, stored key, `Fetch specs` adoption) for deployments that pick DO live. With a route present but no key stored, the Models page and the window name the route's missing credential.
- `llm-deepseek` remains active and deepseek-official selectable with a stored `DEEPSEEK_API_KEY`.
- The tuning rail entry renders above the Efficiency entry; its provider select lists both adapter families from the joined configurable directory, each row naming its settings address, and switches the table to that route's catalog; the current row's Temp and Effort commits survive reload and mirror into the composer slider and seat; any row's capacity and tune cells write their stored nodes, the route row's Format/Endpoint/API-key fields write `api`/`baseURL` and the credentials seam as Settings → Models does, the $/M block renders the session-stats pricing map read-only, and all converge with the Models page editor and the cost chip after `llm/adapters-updated` / `settings/document-updated`, and a schema-refused value surfaces the Host diagnostic without touching any stored node, with the window's cells applying the same rules live (temperature `[0, 1]`, K/M capacity parse, max ≤ context, context ≤ `maxContextWindow`) by painting the offending cell without a commit; `Fetch specs` re-runs `llm/discoverModels` additively — a prefetch leaves every existing row's stored cells untouched and appends only unknown ids with the adapter capacity defaults — while rates keep the shipped per-route table; choosing a model in the composer applies that model's stored tune where the selection omits a knob, in precedence explicit selection over tune over deployment default.
- `verify-client-ui-i18n`, `verify-client-catalog`, and the existing token-efficiency and model-selection client specs stay green.

## Risks

- A fresh boot shipped with the DO default but no DO credential starts on a route that fails MISSING_CREDENTIAL; the first-run onboarding today ends at the deepseek-official key prompt only, so the Models row and the window must carry the DO-key guidance until onboarding grows a second prompt.
- Capacity edits are deployment-wide by construction; an operator who expects per-session scope widens one session and every session. The window's copy states the scope, and a true session-scoped override stays a seam change out of scope here.
- The hand-declared `models` list is positional in stored YAML, so each table row must resolve its model's index with the same schema operations the Models page uses; divergence between the two writers is bounded by the shared expected-revision fence (`settings/conflict`).
- The additive merge deliberately trades staleness for ownership on known ids: an endpoint that renames a model id appears as a new row beside the old one, and endpoints never prune stored rows — removing a model stays a manual Models-page act, so a renamed gateway can leave an orphan row until the operator deletes it.
- A table over eleven DO models reads as the efficiency window's spend table until the head, warn strip, and legend name its scope; the mock carries all three, and an implemented surface should keep them.
- Three writers can name a session's temperature and effort — an explicit selection, a stored tune, the deployment default — so the merge order must live in the single place that applies `agent-default-model` today; the acceptance criteria pin it there.
- DO publishes rates in documentation, not at the endpoint; the shipped table is a dated snapshot (docs verified 2026-10-01) and rate corrections enter the session-stats pricing row, never the tuning table — implementations and copy must never present fetched specs as including money.
- The picker can show routes whose credential is absent (openai, anthropic); selecting one renders the table with refused state for operations that need a key, matching the Models page's credential badge, while capacity and pricing edits stay keyless.
