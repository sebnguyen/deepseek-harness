# Agent Note: 持久化的请求线上报文捕获

Status: implemented

[English](2026-09-25-durable-request-wire-capture.md) | 中文

## 问题

此前没有任何持久化记录保存适配器实际发到线上的内容。日志已经承载请求信封（`request/header`：调用配置、适配器默认值、已装配的工具 schema）以及作为 surface 事件的每条消息，"模型可见即已记录"这一不变量由此得到满足。但序列化后的请求体还取决于日志之外的东西：序列化之后合并进来的提供方扩展字段、每次调用铸造的 Files API `file_id`，以及一次尝试在回退后最终采用的图片表示形式——这些都在派发时解析，任何地方都没有记录。

因此诊断一次提供方请求，要么重新推导并寄希望于重建结果恰好一致，要么挂调试器。那些只有精确字节才能解释的后端拒绝——字段被拒、文件 id 过期、表示形式不符预期——事后完全无法诊断。

## 决策

`SessionEventMap` 新增一个仅记录型（log-only）成员 `request/wire`，承载 `RequestWireRecord`：提供方路由、模型、可选的提供方中立用途、图片表示形式，以及精确的请求体文本。

记录请求体的是适配器，而不是 agent loop。`DeepSeekAdapterOptions` 新增 `onWireRequest`，在完整请求体唯一存在的时刻调用——即 `JSON.stringify({ ...body, ...extensions.fields })` 之后、`fetch` 之前。该钩子对每一次真正抵达传输层的尝试触发一次，因此在文件解析阶段就失败的尝试不会被记录。

`llm-deepseek` 负责接上该钩子并自行追加事件：用 loop 已经在每个请求上打标的 `sessionId`，通过可选的 `ctx.get('sessions')` 服务解析出被寻址的 Session。没有打标 id 的请求，或 id 指向 store 中不存在的 Session 的请求，照常流式发送，不记录任何内容。适配器不掌握任何 Session 知识；只有插件的 `apply` 闭包会触达日志。

Trajectory 标签页把每个捕获到的请求体折叠进它自己的请求检查器标签页，按事件所属的 step 归组，并按派发顺序排列。仅当确实捕获到请求体时该标签页才出现，因此本次改动之前写下的历史日志不会显示一个空标签页。

该事件的读者范围与其同类成员一致：它是核心成员，本仓库的任何构建都能读取它。早于它的构建会拒绝该日志而不是跳过它，这正是预期的失败方式——另一种选择，即 `ignorable` 信封，会让旧构建在静默丢弃读者真正要找的记录的同时重建会话。

## 备选方案

**把请求体存成结构化对象。** 这样渲染和查询都更好，也避免在日志自身的 JSON 里再转义一次请求体。但它丢掉了这次捕获存在的理由：记录下来的将是重新序列化的结果，而不是原始字节。当提供方仅凭原始文本才能解释的拒绝原因出现时，键顺序与空白差异恰恰是关键。

**在浏览器端由已记录事件重建请求体。** 这正是 composition 视图已经为 token 和 KV-cache 分类所做的事，也是最初的提案。它无法做到精确，因为扩展字段、文件 id 和最终表示形式都是宿主运行时状态。一个大多数时候正确、偶尔错误的重建对诊断而言比没有更糟，因为它会静默失效。

**由 agent loop 记录请求体。** loop 冻结请求并记录 `request/header`，所以它天然是请求记录的所有者。但它拿不到完整请求体：序列化发生在适配器内部，在 loop 的请求已被冻结之后。

**在现有的 `agent/assistant-stream` 式实时通道上发出该记录。** 这样请求体完全不进日志，也能避免增长成本。但作为唯一机制被否决了：需求是事后诊断，而仅实时的帧无法在重载或重放后存活。

**把请求体挂到 `request/header` 上。** 否决：`EpochHeader` 是被 `headerEquals` 逐字段比较的重建契约，请求体不属于请求信封身份。把它折进去会让每个请求看起来都像信封变更。

## 后果

日志按每次派发的尝试增长一个请求体，而一个请求体重述了整个 prompt。存储增长在请求数上是二次的：第 *N* 个请求携带了第 1..*N-1* 个请求携带过的全部内容。JSONL 后端默认使用 zstd 压缩，且每个请求重述前一个前缀，因此磁盘开销远低于朴素算术，但它是真实存在的，并随会话长度增长。

`payload` 是精确文本，因此捕获值对字节具有权威性，却不适合结构化查询。想要字段的消费者自行解析。

捕获覆盖经由 DeepSeek 适配器派发的路由。录制会话测试所用的是 replay 适配器，它替换了自己的流式路径，因此重放的 fixture 不携带 `request/wire` 事件，既有的录制快照保持不变。

该事件参与持久化词汇表：`docs/persistence-catalog.md` 与 `packages/core/session/src/known-event-types.ts` 由声明生成，必须在 `pnpm run verify-persistence-catalog` 下保持最新。

本次改动没有收窄任何既有不变量。[Every LLM request is reconstructable from the session log](2026-07-05-reconstructable-requests.zh.md) 约束的是 loop 的 `GenerateOptions` 与 `EpochHeader`，它们仍然可重建；派发的请求体额外包含适配器解析出的字段，本记录捕获这些字段而不是推导它们。
